版: 最終三者整合版
更新日: 2026-08-28

本書は内部仕様の唯一の正本である。現行の構造・処理・分類・適用判定・異常時の扱いだけを第1～18章に記載する。業務仕様と全チェックルールは`docs/外部設計書.md`、変更経緯はGit履歴を参照する。

## 1. 設計原則

### 1.1 正本と優先順位

業務上の適用条件・正常条件・不備時の表示は`docs/外部設計書.md`を正本とする。本書は、その業務仕様を実現するデータ、処理、状態遷移、モジュール責務を定める。料金・販売対象の実行時値は`src/domain/catalog.ts`を正本とし、外部設計書第11章および料金回帰テストと同時に変更する。

実装・テストが外部設計書と異なる場合、業務仕様を実装へ合わせて変更しない。内部設計だけの誤りは本書を修正し、実装の差異は第18章の「実装側残課題」へ記録する。

### 1.2 設計原則

1. 取得、正規化、派生、適用判定、検証、集約、表示、通知、実行制御を分離する。
2. 分類に使用した条件と根拠を同じ処理から返し、検証器で再分類しない。
3. 取得済み空欄と取得不能を型で区別する。
4. 業務不備、判定不能、適用外、対象外、実行失敗、通知失敗を混同しない。
5. ConsoleとSlackは`EventDisplayContext`を共用する。
6. 料金・販売対象の正本は`src/domain/catalog.ts`だけとする。
7. OSIROは読み取り専用、外部通知はインターフェース越しに行う。
8. 過去の判断、レビュー結果、完了履歴を現行仕様と併記しない。現在有効な内容だけを責務を持つ章へ一度記載する。

## 3. 処理フロー

```text
loadEnv / validateOperationalConfig
  → artifact retention
  → previous-count state load
  → browser/context/list page launch
  → list acquisition and pagination quality
  → for each event
      → detail DOM acquisition
      → normalizeEvent
      → deriveEvent
      → buildRulePlans
      → validators
      → aggregateEventStatus
      → EventDisplayContext
  → save count and storageState atomically
  → cleanup pages/browser
  → aggregateSummary
  → Console presentation
  → Slack message plan / dry-run or send
  → createRunOutcome
  → process.exitCode
```

各ステージは`StageResult`へcompleted／partial／failed／skippedとして記録する。詳細取得中の認証切れは後続取得を停止し、一般の詳細1件の取得失敗はそのイベントをUNKNOWNとして後続を継続する。詳細取得の一部失敗、状態保存失敗、cleanup失敗があれば正常終了通知を作らず、取得済み結果を添えた実行失敗通知を作る。業務NGは処理失敗ではないためexitCode 0、取得・認証・状態・cleanup・通知・予期外の技術的失敗はexitCode 1とする。

## 4. データモデルと変換境界

### 4.1 EventInfo

`src/types.ts`の`EventInfo`は取得層が返す未正規化のイベント値である。イベント名、URL、日時、会場、本文、申込締切、`TicketInfo[]`、`fieldAvailability`を持つ。開催方法、料金方式、券役割、対象外状態は持たない。

OSIRO画面でDOMが存在して値が空欄なら`null`、DOM・通信・解析の問題で取得できなければ`undefined`と`fieldAvailability=false`を返す。チケットにはDOM順で`ticket-1`、`ticket-2`のIDと1始まりの`position`を付ける。画面から永続IDを取得できるようになっても、Console・Slackの券番号はDOM順を使用する。

### 4.2 ObservedField

```ts
type ObservedField<T> =
  | { state: "present"; value: T; rawValue?: string }
  | { state: "empty"; rawValue?: string }
  | { state: "unavailable"; reason: string }
  | { state: "invalid"; rawValue: string; reason: string };
```

`undefined`を空欄へ変換しない。DOMが存在して値が空ならempty、DOM・通信・解析で取得できないならunavailable、不正形式ならinvalidとする。金額欄は空欄をempty、整数に変換できない入力をinvalid、DOM自体を取得できない状態をunavailableとする。

### 4.3 入力から出力までの正本モデル

| フェーズ | 正本モデル | 次のフェーズへ渡す内容 |
| --- | --- | --- |
| 一覧取得 | EventListItem | イベント名、正規化済み詳細URL |
| 詳細取得 | EventInfo／TicketInfo | 画面の値とfieldAvailability |
| 正規化 | NormalizedEvent／NormalizedTicket | 全画面項目をObservedFieldへ変換した値 |
| 対象・分類 | DerivedEvent／DerivedTicket | EligibilityDecision、EventAttributes、券役割、rateKey、TicketSets、根拠 |
| 適用判定 | RulePlan | ruleIdごとのapplicable／skipped／unknownと対象券 |
| 検証 | ValidationResult | passed／failed／unknown／skipped、検査項目、期待値・実際値・表示理由 |
| イベント集約 | EventValidationOutcome／EventDisplayContext | EventStatus、表示に必要なイベント・券・不備情報 |
| 実行集計 | RunSummary | 対象、対象外、対象判定不能、OK、NG、UNKNOWN、NG＋UNKNOWN |
| 通知 | NotificationOutcome | 計画、送信済み・未送信ID、試行回数、失敗理由 |
| 実行終了 | RunOutcome | StageResult、RunFailure、集計、通知結果、exitCode |

各フェーズは直前の正本モデルだけを入力とし、後段で画面値の取得やイベント・券の再分類を行わない。

## 5. 追跡モデル

### 5.1 ObservedReference

参照元をeventId、ticketId、チケット位置、確認場所、field、source、target、path、stateで表す。sourceはLIST_PAGE、DETAIL_PAGE、CONFIG、STATE_FILE、DERIVEDである。Cookie、token、Webhook URL、HTML全文、不要な本文全文を保持しない。

### 5.2 DerivationEvidence

ObservedReference、比較方法、期待パターン、判定理由を保持する。eligibility、deliveryMode、pricingMode、pricingScheme、beginner、seriesEvent、全回・途中参加属性、appliedComposition、全券役割、rateKey、参加形態、各券集合に設定する。determined値に理由のない空配列を許可しない。

### 5.3 RulePlan.applicabilityReferences

全RulePlanは適用判定に使った派生属性、券、券集合、設定のObservedReferenceを持つ。applicable、skipped、unknownのすべてで根拠を追跡できる。定数による廃止ルールはCONFIG参照と理由を持ち、架空のチケット参照を作らない。

### 5.4 ValidationResult.inspectedFields

適用されたpassed／failed／unknownは、実際に検査したイベント・本文・券・券集合・比較対象を保持する。skippedは検査していないため空でよいが、applicabilityReferencesとreasonを持つ。failed／unknownからチケット位置と画面項目まで辿れる。

## 6. 派生モデル

`DerivedEvent`はNormalizedEvent、EligibilityDecision、EventAttributes、DerivedTicket、TicketSets、TicketSetEvidenceを持つ。

### 6.1 EligibilityDecision

イベント名を取得でき、`予告`、`一覧`、`事務局決済`のいずれかを含めば`excluded`とし、全業務ルールを実行しない。イベント名を取得できなければ`undetermined`とし、対象イベントへ推測で含めない。それ以外は`target`とする。`EligibilityDecision`を対象判定の正本とし、取得層は詳細画面のHTTP・認証・タイトルDOMを確認した後、この条件に該当するイベントの後続フォーム取得を省略するためだけに参照する。

### 6.2 EventAttributes

| 属性 | 導出方法 |
| --- | --- |
| deliveryMode | 本書16.2節の会場・イベント名判定 |
| pricingMode | 本書6.4節の料金比較券群と金額判定 |
| pricingScheme | 通常料金の場合だけ、通常参加券群の料金区分と金額を料金カタログへ照合 |
| beginner | イベント名または券名に`初心者読書会`、`初心者限定`、`ビギナー限定`のいずれかが部分一致 |
| seriesEvent | イベント名が正規表現`全\s*[0-9]+\s*回`に一致 |
| hasAllSessionEntry | 全券の役割確定後、all-session-entryが1件以上 |
| hasPartialEntry | 全券の役割確定後、partial-entryが1件以上 |
| appliedComposition | applicationTicketSet内のalready-appliedが0件ならnone、全件ならalready-applied-only、それ以外はmixed |

全属性は`DerivationResult<T>`でdetermined／unknown／conflictを表す。導出に必要な画面項目・券役割・金額を確定できなければunknown、相反する候補があればconflictとし、standardやonlineへ黙ってフォールバックしない。

### 6.3 チケット役割と集合

役割：member-entry、plan-change、operation-member、already-applied、all-session-entry、partial-entry、fixed-onsite-entry、fixed-online-entry、unclassified。各役割の導出条件と併記可否は本書16.6節を正本とする。

| `TicketSets` | 所属する券 |
| --- | --- |
| pricingComparisonSet | plan-change、operation-member、already-applied、all-session-entry、partial-entryの候補をいずれも持たない券 |
| applicationTicketSet | plan-change・operation-memberではなく、member-entry、already-applied、all-session-entry、partial-entryのいずれかを持つ券 |
| regularEntrySet | pricingComparisonSetのうちmember-entryを持つ券 |
| allSessionSet | all-session-entryを持つ券 |
| partialEntrySet | partial-entryを持つ券 |
| nonAppliedPartialSet | partial-entryを持ちalready-appliedを持たない券 |
| appliedPartialSet | partial-entryとalready-appliedを持つ券 |
| appliedSet | already-appliedを持つ券 |

オンライン案内の適用根拠として、プラン変更券以外を`onlineGuidanceCandidates`、そのうち「オンライン開催する」がONの券を`onlineUrlTargets`、プラン変更券以外（運営メンバー券だけはONの場合）を`notificationTargets`として保持する。検証器は派生済みの役割・集合を受け取り、券名や金額から再導出しない。

`already-applied`でオンライン参加URLが`https://nekomachi-club.com/events/`配下の券は、CROSS-001/002の券間比較集合からだけ除外し、個別のURL・お知らせ・締切および本文との一致確認からは除外しない。金額はこの除外判定に使わない。

### 6.4 金額による分類と検出限界

`pricingComparisonSet`が1件以上あり、全券の金額が同一なら固定料金、0件または複数の金額が混在すれば通常料金とする。通常料金では、通常参加券群の全券が各料金区分のゲスト料金に一致する場合だけゲスト料金とし、一部一致は通常料金として各券の金額検査へ進める。

この分類は画面の登録値から作成者の意図を完全には復元できない。通常料金の全比較券を誤って同額にすると固定料金、金額の異なる固定料金は通常料金、通常料金の全券を誤ってゲスト料金にするとゲスト料金、ゲスト料金の1券でも金額を誤ると通常料金になる。これらは回答済み仕様による検出限界であり、別の推測条件で補正しない。

## 7. RulePlanと検証

`buildRulePlans`は派生済み属性・役割・券集合だけを参照し、ruleId、eventId、ticketIds、applicability、applicabilityReferences、reasonを持つRulePlanを全ルール分生成する。検証器はRulePlanが`applicable`の場合だけ値を比較し、`skipped`／`unknown`は共通処理でそのままValidationResultへ変換する。

| 実装 | 判定単位 | 担当ID |
| --- | --- | --- |
| `validation/event-setting.ts::validateEventSettings` | イベント設定 | EVT |
| `validation/body.ts::validateBody` | 本文 | BODY |
| `validation/ticket.ts::validateTickets` | チケット1件 | TKT |
| `validation/ticket-set.ts::validateTicketSets` | チケット集合 | SET |
| `validation/cross-ticket.ts::validateCrossTicket` | 複数チケット間 | CROSS |
| `validation/cross-area.ts::validateCrossArea` | 本文とチケットなど複数箇所間 | AREA |

廃止互換のTKT-005・TKT-014を含む38ルールのIDは`src/domain/derive.ts`の`BUSINESS_RULE_IDS`を実装上の一覧とし、全IDの対応は第17章を正本とする。業務ルールは独立して評価し、同じ入力が複数ルールの不備条件を満たしても抑止しない。一方、同じルール結果を二重生成する実装不備は`ruleId + eventId + ticketIds`を一意キーとして例外にする。

## 8. 集約と表示正本

### 8.1 EventDisplayContext

イベント表示の唯一の正本である。

- eventId、detailUrl
- name、startAt
- 派生済みdeliveryMode
- eligibilityStatusと理由
- eventStatus
- ValidationResult
- ClassificationDiagnostic
- 表示用ticketId、位置、券名

取得失敗もEventDisplayContextへ、取得品質のunknown ValidationResultと取得不能ObservedReferenceを設定して表す。別の旧結果型や一方向変換層は存在しない。

### 8.2 RunSummary

targetLabel、executionComplete、acquisitionComplete、checkedCount、excludedCount、undeterminedCount、okCount、ngCount、unknownCount、failedAndUnknownCount、EventDisplayContext配列、executedAtを持つ。イベントは開始日時降順、日時不明を末尾に並べる。

集計式の正本は次のとおりとする。

- `checkedCount = okCount + ngCount + unknownCount + failedAndUnknownCount`
- `一覧取得総数 = checkedCount + excludedCount + undeterminedCount`
- excludedとundeterminedはcheckedCountへ含めない。
- 「すべてOK」は実行・取得が完全、checkedCountが1件以上、undeterminedCountが0件、NG・UNKNOWN・NG＋UNKNOWNが0件の場合だけ表示する。

### 8.3 RunOutcome

実行結果の唯一の正本である。runStatus、executionStatus、acquisitionStatus、StageResult、EventDisplayContext、RunSummary、NotificationOutcome、RunFailure、exitCodeを持つ。

| 内部状態 | 意味 |
| --- | --- |
| executionStatus completed／failed | 技術的な実行が完了したか。業務NGだけではfailedにしない |
| acquisitionStatus complete／partial／failed | 一覧・詳細取得の完全性 |
| runStatus success | 技術的失敗も業務上の異常もない |
| runStatus business-failure | NG、UNKNOWN、NG＋UNKNOWNのいずれかがあるが技術的実行は完了 |
| runStatus partial-success | 詳細の一部を取得できなかった |
| その他のrunStatus | acquisition／authentication／state／notification／cleanup／unexpectedの主失敗を表す |
| exitCode 0／1 | executionStatusがcompletedなら0、failedなら1 |

### 8.4 結果区分の対応

| 状態 | 内部表現 | 集計・実行への影響 |
| --- | --- | --- |
| 業務設定が正しい | ValidationResult `passed` | 対象イベントの全適用ルールがpassedまたはskippedならOK |
| 業務設定が不備 | ValidationResult `failed` | NG |
| 取得・解析・分類不能 | ValidationResultまたはClassificationDiagnostic `unknown` | UNKNOWN。passedへ変換しない |
| 不備と確認不能が併存 | EventStatus `failed-and-unknown` | NG＋UNKNOWN。NGまたはUNKNOWNへ片寄せしない |
| ルール適用外 | ValidationResult `skipped` | OK・NG・UNKNOWNの原因にしない |
| イベント全体が対象外 | EligibilityDecision `excluded` | チェック対象数に含めず、対象外数へ加える |
| 対象外か判断不能 | EligibilityDecision `undetermined` | チェック対象数へ含めず、対象判定不能として別集計・表示 |
| 実行処理失敗 | RunFailureとexecution failure | exitCode 1。正常終了通知を作らない |
| Slack送信失敗 | NotificationOutcomeとnotification failure | exitCode 1。業務結果自体は変更しない |

## 9. ConsoleとSlack

ConsoleとSlackはRunSummary内の同一EventDisplayContextを参照する。表示層で対象外や開催方法を判定しない。ValidationResultとClassificationDiagnosticからオシロ管理者向け明細を作る。

券単位・券集合の明細は、構造化されたticketIdsから券番号・券名を見出しへ1回だけ表示し、検証メッセージ内の同一情報を除く。CROSS-001/002は見出しをルールIDだけとし、検証メッセージに不一致グループの券番号を表示する。ConsoleとSlackは同じ整形処理を使用する。

Slackは3,840文字を安全上限としてイベント境界で分割する。長い1イベントだけは改行境界、必要なら文字境界で分割する。各メッセージIDは本文hashを含む安定IDである。Slack本文生成、Console表示、Slack送信は別処理とし、送信処理は`SlackTransport`越しに呼び出す。

## 10. Slack送信計画

`SlackProgressState`はplanId、targetHash、各メッセージのid、textHash、unsent／sending／sent、未送信本文、Slack tsを保持する。`logs/slack-notification-progress.json`へ一時ファイルからのrenameで原子的に保存し、token、Cookie、チャンネル平文を残さない。通知先はhash化し、送信後の本文は削除する。

送信順：

1. 既存状態を読み、破損なら送信前に停止。
2. 前回planにunsentがあれば、その本文だけを再送。
   前回planが未完了のまま次回の本文が変わっても、保存済みの未送信分だけを完了し、その呼出しでは新planを送らない。
3. 新規planを送信前に保存。
4. 各本文をsendingとして保存してから送信。
5. Slack成功後、tsとsentを保存し、本文を削除。
6. 429・5xx・通信例外だけを最大3回、待機して再試行。
7. 恒久エラーは即時notification failure。
8. Slack成功後の状態保存失敗は送達不明として自動再送しない。

通常送信では`SLACK_BOT_TOKEN`と`SLACK_CHANNEL_ID`を必須とし、未設定を通知成功またはチェック不要へ変換しない。`SLACK_DRY_RUN=true`では取得からSlack本文分割・結果集約まで行うがSlack APIと進捗保存を呼ばず、トークンとチャンネルを必須にしない。

## 11. 取得品質と画面待機

### 11.1 一覧

起点URLは`EVENT_LIST_URL`の1つだけとする。次リンクを辿り、query順とhashを含めて正規化したURLで再訪、循環、重複を検出する。最大20ページ。各遷移はDOMContentLoaded、HTTP、ログイン、`#eventIndex`、URL前進を確認する。

一覧内のリンクは`/admin_events/{id}/edit`だけを候補にし、編集操作名・参加者・分析・チケット管理などのリンクと、削除・非公開・複製などの操作リンクを除く。詳細URLはqueryとhashを除いて正規化し、同一URLが複数ある場合は、書名括弧、イベントを示す語、編集URL形式を使った表示名スコアが最も高い1件を残す。重複除去後が0件ならQUAL-LIST-006のexecution failureとする。

### 11.2 詳細

1. `page.goto(..., waitUntil: "domcontentloaded")`
2. HTTP成功
3. `/login`でないこと
4. URLと値入りの`#title`による詳細画面識別
5. 対象イベントでは開始・終了日時の値、会場欄、本文欄
6. チケットコンテナまたは`event_ticket_name`
7. 全チケットの券名、料金、販売対象、オンライン開催設定
8. 各フィールド抽出とavailability設定

継続通信の終了を待機条件にしない。固定sleepを使用しない。DOMタイムアウトはQUAL-DETAIL-003〜006の理由付き取得失敗となり、EventDisplayContextのUNKNOWNへ変換される。対象外イベントはタイトル値の確定後に後続フォームを取得しない。チケット領域が先に表示されても、各券の必須コントロールが揃うまでは抽出へ進まない。

フォームは1回のブラウザ内評価で抽出し、チケットを得られなかった場合だけLocatorによる券単位抽出を補助経路として使用する。補助経路で取得できた券とavailabilityを一次結果へ統合する。詳細取得と失敗artifact保存は同じPageを共有し、Pageの終了と終了失敗の記録は実行制御が行う。

チケット集合を正常に走査できた結果が0件なら取得品質エラーにはせず、SET-014を`failed`とする。チケット集合自体を取得できなければQUAL-DETAIL系の取得失敗とSET-014の`unknown`を区別する。

## 12. 状態保存とcleanup

前回件数状態は不存在だけを初回とし、破損、不正値、読取不能をexecution failureとする。保存は一時ファイル作成、書込、renameで行い、失敗時に旧状態を保持する。前回10件以上かつ今回50%未満を取得異常とする。

認証状態は実行終了時に一覧画面固有DOMと非ログインURLを再確認できた場合だけ、一時ファイルへ書き、JSON検証後に置換する。認証切れ後は書き戻さない。書込・JSON検証・置換の失敗時は旧`storageState.json`を保持し、execution failureとする。

詳細ページは各イベントのfinallyで閉じる。一覧ページとブラウザは外側finallyで閉じる。1リソースのclose失敗後も残りを閉じ、全cleanup失敗をRunOutcomeへ保持する。

## 13. artifact

`src/artifacts/manager.ts`が唯一のartifactライフサイクル実装である。

- root：`artifacts/`
- 既知の削除対象：`screenshots/*.png`、`html/*.html`、`json/*.json`
- 初期保存期間：30日
- 設定：ARTIFACT_RETENTION_DAYS、ARTIFACT_CLEANUP_ENABLED
- 期限判定：`mtime < now - retentionDays`
- 境界日時は保持
- retention 0は現在時刻より古い既知artifactを削除
- 不明ファイル、ディレクトリ、symlink、root外は保持
- `storageState.json`と`logs/*.json`は別領域で削除対象外
- directory mode 0700、file mode 0600
- 準備、権限、検査、削除失敗はArtifactOperationError

障害HTMLはhidden/password、CSRF、Slack token、Webhook URLを除去してから保存する。screenshotは機械的除去できないためprivate権限と保存期間で保護する。

## 16. 画面項目の読み取り・分類仕様

外部設計書にはオシロ管理者が確認する業務内容だけを記載し、HTML、正規表現、表記統一、分類順序は本章を正本とする。

### 16.1 表記の統一

- イベント名・券名は全角数字を半角へ変換し、`〖〗`を`【】`、全角空白を半角空白、連続空白を1個へ統一し、前後の空白を除く。
- 券名の丸括弧は全角・半角を半角へ統一する。
- 金額は通貨記号、カンマ、`円`、`税込`、空白を除いて整数として読み取る。
- 販売対象は`オン / オフ / ハイ / 外 / A / U-22 / B`の集合へ統一する。
- 画面の原文は判定根拠として保持する。

### 16.2 開催方法

1. 対象外判定後、会場が正規表現`オフ会場\s*[+＋]\s*オンライン`に一致すればハイブリッド。
2. それ以外で、空欄ではないイベント名に`【東京】 / 【大阪】 / 【京都】 / 【福岡】 / 【名古屋】 / 【愛知】 / 東京開催 / 文学フリマ / 猫町.で、旅をしよう`のいずれかが部分一致すればオフライン。
3. 会場とイベント名を取得でき、上記に該当しなければオンライン。
4. 会場を取得不能でハイブリッドを除外できない場合、または会場がハイブリッド表記ではなくイベント名が空欄・取得不能の場合は確認不能。

`【福岡 第N回】`だけをオフラインとする正規表現判定は行わない。

### 16.3 本文の参加費欄

本文HTMLは`br`と`p`・`div`・`li`・`h1`〜`h6`・`tr`の終了位置を改行へ変換してから`textContent`を取り出す。改行以外の連続空白を1個へ統一し、連続する空行を1改行へまとめる。

統一後の本文で、行頭が正規表現`^(?:(?:■|●|◆|🔴|◾️?)\s*)?(?:読書会)?参加費(?=$|[\s:：（(])`に最初に一致する位置から、次の記号付き見出しまたは`#`付き見出しの直前までを参加費欄とする。コロン後の同一行も参加費欄へ含める。

参加費欄を改行または句点で分け、金額表記`無料`または`[0-9０-９,，]+円`と、会員名・回数区分・初参加区分を抽出する。`無料`は0円、全角数字等は整数へ統一する。対象者を省略した回数記載は、直前の金額記載で対象者が明示され、回数区分だけを一意に置き換えられる場合に限って継承する。`猫町スクール`または申込み済み参加者向けの個別料金を示す行は、通常本文料金の抽出から除外する。

本文が空欄、または本文を取得済みで参加費欄が0件の場合はBODY-003/004をチェック不要とする。参加費欄がある場合は、必須料金区分の不足・金額不一致・形式不正を`failed`とする。参加費欄に正規表現`(?<![0-9])1回目`と`(?<![0-9])2回目`がともに0件ならBODY-001/002をチェック不要とする。HTML構造または本文欄を取得不能なら依存ルールを確認不能とする。

### 16.4 書名・締切時刻・受付開始時刻

- 書名はイベント名・券名の対応する括弧`『』`、`「」`、`《》`、`〈〉`から抽出し、完全一致する`読書会なし`、`読書会セット`を除く。イベント名では重複除去後に文字数が最長の候補、券名では全候補を保持する。イベント側の最長候補が同数で複数なら確認不能。
- お知らせの申込締切は、全角数字・全角コロンを半角へ統一し、任意の日付に続く`H:MMまでに`または`H時MM分までに`の全出現をHH:MMへ統一する。
- 本文の受付開始は`H:MM 受付開始`、`受付開始 H:MM`と各「H時MM分」形式を抽出する。
- お知らせの受付開始は`H:MMから/より受付開始・受付オープン`、前後を入れ替えた同形式、または`読書会/イベント開始N分前から受付`を抽出し、開催日時からHH:MMを計算する。

### 16.5 料金区分の読み取り

- 参加形態は券名の`読書会のみ参加`、`懇親会まで参加`の部分一致。両方なら矛盾、どちらもなければ「該当なし」。
- 初参加区分は券名の`初参加`の部分一致。
- 回数区分は長い文言から順に`今月2回目以降`、`2回目以降`、`今月1回目`、`1回目`、`2回目`を確認する。1回目系と2回目系の両方があれば矛盾。
- 券名の会員種別は`ハイブリッド会員`、`地域会員`、`オンライン会員`、`非会員`をそれぞれ部分一致し、すべて保持する。ただし会員種別の正本は販売対象であり、券名への会員種別記載は必須にしない。
- 料金区分は開催方法、販売対象のオン・オフ・ハイ・外、券名の回数区分・初参加区分から`src/domain/catalog.ts`のrateKeyへ対応付ける。券名の会員種別、金額、「オンライン開催する」の設定は料金区分判定に使わない。

| 開催方法 | 販売対象 | 券名条件 | rateKey |
| --- | --- | --- | --- |
| オンライン | ハイ | 問わない | ON-HYBRID |
| オンライン | オフ | 問わない | ON-LOCAL |
| オンライン | オン | 1回目系 | ON-ONLINE-1 |
| オンライン | オン | 2回目系 | ON-ONLINE-2 |
| オンライン | 外 | 初参加なし | ON-NONMEMBER |
| オンライン | 外 | 初参加あり | ON-NONMEMBER-FIRST |
| オフライン／ハイブリッド | オフ | 1回目系 | OFF-LOCAL-1 |
| オフライン／ハイブリッド | オフ | 2回目系 | OFF-LOCAL-2 |
| オフライン／ハイブリッド | ハイ | 1回目系 | OFF-HYBRID-1 |
| オフライン／ハイブリッド | ハイ | 2回目系 | OFF-HYBRID-2 |

### 16.6 チケット用途の判定

用途は2段階で判定する。第1段階で料金比較から除く用途を確定し、料金方式判定後の第2段階で固定料金の参加経路を追加する。TKT-018とDIAG-ROLE-001は第2段階完了後だけ生成する。

| 用途 | 判定条件 | 優先順位・併記 |
| --- | --- | --- |
| プラン変更券 | 券名に`プラン変更後`、`新プラン切り替え後`、`プラン切り替え後`のいずれかに続いて`にお申込み`または`にお申し込み`、さらに`下さい`または`ください`が部分一致 | 優先順位1。他用途との併記禁止 |
| 運営メンバー券 | 券名に`運営メンバー`が部分一致 | 優先順位2。ほかの用途との併記禁止 |
| 申込み済み券 | 正規表現`お申し込み済み?の方`が部分一致 | 優先順位3。参加券、全回券、途中参加券と併記可 |
| 全回券 | 正規表現`全\s*[0-9]+\s*回`が部分一致 | 優先順位4。参加券、申込み済み券と併記可 |

| 固定料金の現地参加券 | ハイブリッドかつ固定料金の料金比較券群で、券名に`現地参加`が部分一致 | 優先順位6。参加券と併記可 |

全回券と途中参加券、固定料金の現地参加券とオンライン参加券を同一券へ併記することは禁止する。禁止された組み合わせでも候補を捨てず、TKT-018の根拠へ保持する。

## 17. ルール適用・確認不能の対応

外部設計書は業務上の適用条件、正しい状態、修正内容の正本とする。本章は、その判定に必要な内部入力と、値を取得・分類できなかった場合の扱いだけを定める。業務上の正解条件を本章で再定義しない。

外部設計書の有効ルール36件に、実装互換の常時skippedルールTKT-005・TKT-014を加えた38件を、`BUSINESS_RULE_IDS`、RulePlan、本章の各行で1対1に対応させる。EVT・BODY・AREAは17.2節、TKTは17.3節、SET・CROSSは17.4節が追跡表の正本である。

### 17.1 共通境界

- 外部設計書の適用条件を満たさないと確定できた場合は`skipped`とする。
- 適用可否を決める属性・券役割・券集合を確定できない場合は、該当RulePlanを`unknown`とする。通常イベントなどへ推測で振り分けない。
- RulePlanが`applicable`で、検査する画面項目自体を取得できない場合はValidationResultを`unknown`とする。
- 画面項目を取得できたうえで、必須値が空欄、形式不正、不一致の場合は`failed`とする。結果の独立評価と一意性は第7章に従う。
- 各結果は、適用判定に使った`applicabilityReferences`と実際に検査した`inspectedFields`を保持する。

## 18. 実装側残課題

外部設計・本書・実装の差異として残っている課題はない。新たな差異を発見した場合は、外部仕様を実装へ合わせて変更せず、根拠、正しい内部設計、影響、必要な回帰テストを本章へ記録する。
