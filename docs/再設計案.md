# イベントページ自動チェック 再設計案 第3版

## 1. 目的

現行の外部設計書、内部設計書、ソースコード、テストを調査し、取得、導出、業務検証、集約、通知を分離して再構築する。本書の承認前に本番コード、テスト、設定ファイルは変更しない。

仕様は `confirmed`（資料が一致）、`conflict`（資料が不一致）、`undecided`（業務判断が必要）に分ける。現行実装を無条件に正解とはしない。

## 2. 改訂前の問題と根本原因

現行の `checkEventInfo` は、事実導出、属性判定、ルール選択、全粒度の検証、例外処理、結果集約を同時に担当する。`途中参加 → 全件申込済み → 全N回 → 1チケット → 固定費 → 通常` という早期return順が暗黙の仕様になっている。

第2版にも次の問題が残っていた。

- 全回券と途中参加券を排他的なシリーズ分類にしていた。
- 属性値と `DerivationResult` の両方にunknownを持たせていた。
- 1チケット無料ルールを業務確認に委ね、ルール一覧から落としていた。
- 技術設計と業務判断を同じ質問票で利用者へ質問していた。
- Slack本文生成と送信処理を同じモジュールに置いていた。
- 取得済みだが未知の券と、取得不能で分類できない券を区別できていなかった。

## 3. 処理分類

| 分類 | 目的 | 主なモデル | 例 |
| --- | --- | --- | --- |
| 実行・運用 | CLIを安全に開始・終了する | `StageResult` | 設定、ブラウザ、終了コード、状態保存 |
| 取得品質 | 入力と全件性を信頼できるか確認する | `FetchIssue`, `ObservedField` | HTTP、認証、DOM、件数急減 |
| 変換・正規化 | 生値を意味を失わず変換する | `ObservedField<T>` | 日時、金額、タグ、URL |
| 属性・事実導出 | 独立属性と券の役割を導出する | `DerivationResult<T>` | 開催形態、料金体系、券種 |
| 業務検証 | 取得済み設定を期待値と比較する | `ValidationResult` | 金額、対象、URL、締切、書名 |
| 集約・表示・通知 | 結果を失わず伝える | `RunOutcome`, `NotificationResult` | 件数、本文生成、Slack送信 |

`ValidationRule` と `ValidationResult` は業務検証だけに使う。

## 4. 取得状態モデル

```ts
type ObservedField<T> =
  | { state: "present"; value: T; rawValue?: string }
  | { state: "empty"; rawValue?: string }
  | { state: "unavailable"; reason: string }
  | { state: "invalid"; rawValue: string; reason: string };
```

| 状態 | 意味 | 原則 |
| --- | --- | --- |
| present | 項目と値を取得し解析成功 | 検証する。falseと0も値として保持 |
| empty | 項目は存在するが未入力 | 必須なら設定不備 |
| unavailable | DOM変更や権限等で項目を観測不能 | 依存項目を「確認できなかった」とする |
| invalid | 生値はあるが解析不能 | OSIROの入力不正なら設定不備、抽出器の問題なら確認不能 |

EventとTicketの各フィールドは `ObservedField` で保持する。取得層が状態を作り、正規化層はrawValueを残す。業務対象なのに必要値がunavailableなら、そのルールだけ判定不能にし、独立した検証は続ける。

## 5. 導出結果モデル

```ts
type DerivationResult<T> =
  | { state: "determined"; value: T; evidence: DerivationEvidence[] }
  | { state: "unknown"; reason: string; evidence: DerivationEvidence[] }
  | { state: "conflict"; candidates: T[]; evidence: DerivationEvidence[] };
```

属性値そのものにunknownを含めない。取得不能は `unknown`、取得した複数根拠が矛盾する場合は `conflict` とする。

```ts
type EventAttributes = {
  targetState: DerivationResult<"target" | "excluded">;
  deliveryMode: DerivationResult<"online" | "offline" | "hybrid">;
  pricingScheme: DerivationResult<"normal" | "guest">;
  beginner: DerivationResult<boolean>;
  seriesEvent: DerivationResult<boolean>;
};
```

## 6. 独立したチケット集合属性

単一の `TicketCollectionMode` は使わない。

```ts
type TicketSetAttributes = {
  cardinality: DerivationResult<"single" | "multiple">;
  pricingMode: DerivationResult<"standard" | "fixed-fee">;
  seriesOfferings: {
    hasAllSessionEntry: DerivationResult<boolean>;
    hasPartialEntry: DerivationResult<boolean>;
  };
  specialComposition:
    DerivationResult<"none" | "mixed" | "already-applied-only">;
};
```

`standard` は残余分類ではなく、会員プラン別の料金・販売対象へ対応付ける料金方式を表す。全回券と途中参加券は同時に存在できるため、2つのbooleanを独立して保持する。

### 6.1 チケット集合属性の決定表

| 軸 | 値 | 意味 | 判定材料 | 他軸との併存 | 不明・競合 | 適用ルール群 |
| --- | --- | --- | --- | --- | --- | --- |
| cardinality | single / multiple | 券が1件か複数か | 取得済み券数 | 全軸可 | 集合取得不能ならunknown | 単券無料、構成充足、券間比較 |
| pricingMode | standard | 会員プラン別方式 | 特殊券を除いた券と料金表の対応 | 全軸可 | 固定費根拠と矛盾ならconflict | 標準構成・金額・対象 |
| pricingMode | fixed-fee | 全会員対象の固定費方式 | 対象タグ、プラン変更券、券構成 | 全軸可 | standard根拠と矛盾ならconflict | 固定費構成・対象。通常料金との照合はしない |
| hasAllSessionEntry | true / false | 全回分の参加券がある | 全N回の券名と役割 | 途中参加券と可 | 根拠不足はunknown | 全回券構成・金額除外 |
| hasPartialEntry | true / false | 途中の回から参加する券がある | 第M回から参加の券名 | 全回券と可 | 根拠不足はunknown | 途中参加構成・オンライン設定 |
| specialComposition | none / mixed / already-applied-only | 申込済み券の構成比率 | 券の役割と全件数 | 全軸可 | 役割取得不能ならunknown | 特殊券の適用方針 |

## 7. チケット役割

```ts
type TicketRole =
  | "member-entry"
  | "plan-change"
  | "operation-member"
  | "already-applied"
  | "all-session-entry"
  | "partial-entry"
  | "unclassified";

type TicketRoleAssignment = {
  ticketId: string;
  result: DerivationResult<TicketRole[]>;
};
```

| 役割 | 意味 | 判定材料 | 併存 | 扱い |
| --- | --- | --- | --- | --- |
| member-entry | 会員・非会員の参加券 | 対象、回数、名称 | 全回・途中参加と可 | 標準料金・対象・構成 |
| plan-change | 旧会員向けプラン変更券 | 候補文言 | 原則他役割と排他 | 正式名とA/U-22/B |
| operation-member | 運営メンバー向け券 | 券名 | オンライン対象と可 | 無料、通常構成から除外 |
| already-applied | 申込み済みの人向け券 | 済/済みの文言 | 全回券と可 | 業務回答に基づく除外 |
| all-session-entry | 全回分の参加券 | 全N回の券名 | member-entry等と可 | 全回券向け検証 |
| partial-entry | 途中回から参加する券 | 第M回から参加 | member-entry等と可 | 途中参加向け検証 |
| unclassified | 情報は取得できたが既知役割に該当しない | 取得済み券情報 | 他役割なし | 設定不備候補として通知 |

券情報を取得できず役割を判定できない場合は `unclassified` にせず、導出結果をunknownにして「システムが確認できなかった」とする。

## 8. 技術設計として確定する事項

業務担当者へ質問せず、次を採用する。

1. 全回券と途中参加券は独立して存在を保持し、排他的分類にしない。
2. 属性値にunknownを含めず、`DerivationResult`だけがdetermined/unknown/conflictを持つ。
3. 取得済みの未知券は設定不備候補、取得不能券は判定不能として区別する。
4. `ObservedField`により空欄、取得不能、解析不能、false、0を区別する。
5. ルール適用は独立属性、券集合属性、券の役割、取得状態の小さな条件を合成する。構成別switchや例外early returnは使わない。
6. NGと判定不能を同時に保持し、一方で他方を隠さない。
7. `fatal`は業務検証結果に含めず、実行ステージの失敗として保持する。
8. Slack本文生成は純粋処理、送信・再試行は通知処理として分離する。
9. ログイン切れは以降の全件性を保証できないため、その日のチェック全体が完了しなかったものとして停止・通知する。
10. Slack token未設定とSlack投稿失敗は、通知を業務目的に含むためWindowsタスクを失敗扱いにする。
11. ログイン状態や前回件数の保存失敗も、次回の信頼性を損なうため実行失敗として通知する。
12. 本文だけ取得不能なら、本文依存チェックだけを判定不能とし、他のチェックは続ける。

## 9. 結果モデル

```ts
type ValidationResult = {
  ruleId: string;
  scope: "EVENT" | "TICKET_SET" | "TICKET" | "CROSS_TICKET";
  status: "passed" | "failed" | "unknown" | "skipped";
  severity: "info" | "warning" | "error";
  eventId: string;
  ticketIds?: string[];
  message: string;
  expected?: unknown;
  actual?: unknown;
  reason?: string;
};

type EventValidationOutcome = {
  eventId: string;
  hasFailures: boolean;
  hasUnknowns: boolean;
  results: ValidationResult[];
};
```

許可する組合せはpassed/info、skipped/info、unknown/warning、failed/errorである。fatalはStageResultだけが持つ。

表示状態は正データではなく、2つのbooleanから `ok / ng / unknown / ng-with-unknown` を導出する。NGかつ判定不能のイベントはSlackで両方を別欄に表示し、NG件数と判定不能件数の双方へ数える。重複内訳も併記する。

実行完了、業務不備、判定不能、通知成功は独立保持する。

```ts
type RunOutcome = {
  executionCompleted: boolean;
  stages: StageResult[];
  events: EventValidationOutcome[];
  notification: { status: "sent" | "skipped" | "failed"; reason?: string };
};
```

## 12. ルール適用方式

各ルールは次の4種類の小さな条件から適用計画を作る。

1. 必要なイベント属性
2. 必要な券集合属性
3. 対象となる券の役割
4. 必要フィールドの取得状態

業務上対象外なら理由付きで `skipped`、対象だが必要情報を取得できなければ理由付きで `unknown`、取得済み値が違反なら `failed` とする。1つの巨大な条件式、構成別switch、例外early returnは使わない。

全回券と途中参加券が併存する場合は、両方の存在を保持したまま `VAL-SET-005` と `VAL-SET-006` の対象券群を別々に選ぶ。どちらの券群に何を確認するかは業務確認事項で確定する。

## 14. 新しい処理フロー

1. 実行前提と設定を確認する。
2. OSIROから生データとHTTP/DOMメタデータを取得する。
3. 一覧全件性と各フィールドの取得状態を判定する。
4. 状態を失わず正規化する。
5. イベント属性、券集合属性、券の役割を独立導出する。
6. 全業務ルールについて適用・対象外・判定不能を理由付きで決める。
7. EVENT、TICKET_SET、TICKET、CROSS_TICKETの順に検証する。
8. NGと判定不能を同時保持して集約する。
9. ConsoleとSlack本文を同じRunOutcomeから生成する。
10. Slack送信結果を記録し、運用ポリシーに従って終了する。

## 15. モジュール構成

```text
src/
├─ run/orchestrator.ts
├─ acquisition/
│  ├─ osiro.ts
│  └─ quality.ts
├─ domain/
│  ├─ model.ts
│  ├─ normalize.ts
│  └─ derive.ts
├─ policy/
│  ├─ rules.ts
│  └─ applicability.ts
├─ validation/
│  ├─ event.ts
│  ├─ ticket-set.ts
│  ├─ ticket.ts
│  └─ cross-ticket.ts
├─ results/aggregate.ts
├─ presentation/
│  ├─ console.ts
│  └─ slack.ts
└─ notification/slack.ts
```

全16ファイルで開始する。1ルール1ファイルにはせず、将来必要になった時だけ分割する。

| モジュール群 | 責務 | 入力 | 出力 |
| --- | --- | --- | --- |
| run | 全体順序、ステージ、終了 | 設定 | RunOutcome |
| acquisition | OSIRO取得と品質 | URL、session、raw | ObservedField、FetchIssue |
| domain | 型、正規化、独立属性導出 | raw observations | Event、attributes、roles |
| policy | ルールカタログと適用計画 | ValidationContext | rule plan |
| validation | 粒度別の純粋な業務検証 | context、plan | ValidationResult[] |
| results | NGと判定不能の集約 | 全結果 | EventValidationOutcome、RunOutcome |
| presentation | Console・Slack本文生成のみ | RunOutcome | text/messages |
| notification | Slack送信、再試行、送信結果 | messages | NotificationResult |

## 16. 移行計画

1. `docs/業務確認事項.md` の回答を決定記録として本書へ反映する。
2. 現行テストをlegacy characterizationとして分離し、匿名化fixtureで現行挙動を記録する。
3. `ObservedField`、FetchIssue、ValidationResult、EventValidationOutcome、RunOutcomeを導入する。
4. 取得品質と正規化を分離し、empty/unavailable/invalid/false/0をテストする。
5. 独立属性と券役割をpure functionで導出し、同時成立を組合せテストする。
6. ルールごとの適用理由をfixtureでレビューする。
7. 粒度別ValidationEngineへ段階移行する。
8. NGと判定不能、実行完了、通知失敗の全組合せを検証する。
9. 新旧差分を提示し、承認された差分だけであることを確認して切り替える。

OSIROへの接続や本番相当dry-runは別途承認を得て実施する。

## 17. 第2版からの変更点

| 項目 | 第2版 | 第3版 |
| --- | --- | --- |
| シリーズ方式 | 排他的なシリーズ分類 | 全回券・途中参加券の存在を同時保持 |
| unknown | 属性値と導出結果に二重保持 | DerivationResultだけに保持 |
| 未知券 | 取得不能と混在 | 取得済み未知券はunclassified、取得不能はunknown |
| 1チケット無料 | 業務質問に依存 | VAL-TKT-001として復元 |
| 特殊申込済み | 一部質問のみ | 候補となる全14項目を一覧化 |
| Slack | 本文と送信が同一責務 | presentationとnotificationへ分離 |
| 運用質問 | 技術選択を利用者へ質問 | 安全な推奨案をCodex側で決定 |
| 業務質問 | 技術用語・ルールIDを本文に記載 | 別紙で業務用語だけを使用 |
